# HadaCore strategy as an optional local core

HadaCore may contribute a **local arithmetic core** to cuButterfly without
changing the hierarchical hybrid tile-dataflow method. The distinction is
necessary because the current pinned adapter executes a complete FWHT, while a
local core is one dependency-closed group inside a cuButterfly plan.

## What is reusable

The reusable part is the implementation strategy and its measured resource
parameters:

- register-resident fragments for a local FWHT subtransform,
- Tensor Core `mma.sync` operations where the requested arithmetic contract
  allows them,
- `chunks_per_warp`, `warps_per_block`, and block residency as search dimensions,
- asynchronous global-to-shared movement for a tile, and
- an explicit final scaling step for normalized or unnormalized transforms.

These are core parameters. They do not define the global schedule. The common
planner still chooses the stage group, tile shape, data/time expansion,
producer-consumer layout, boundary swizzle, residency and inter-group
dependency. A design with one local group is a legal endpoint; multiple groups
remain available when the resource model requires them.

## Required provider contract

Before registration in the public FWHT candidate inventory, a provider must
expose the following information and operations:

| Field | Requirement |
| --- | --- |
| Semantic domain | FWHT, direction, storage precision, multiply/accumulation precision, output rounding and normalization |
| Local shape | Power-of-two tile length and the number of dependency-closed stages consumed |
| Layout | Input and output strides, packed/shared layout, boundary swizzle and whether the provider preserves the consumer layout |
| Execution | Device pointers, workspace, CUDA stream, tile count and explicit launch configuration |
| Resources | Registers, static/dynamic shared memory, threads, barriers, scratch bytes and supported SM range |
| Numerical evidence | Same-contract CPU reference, full error distribution and any coefficient or reduction-order differences |
| Provenance | Upstream commit, source hashes, license, local changes and compiled binary hash |

The planner may then construct a candidate containing this provider and surround
it with the ordinary cuButterfly stages. The provider is excluded when any
semantic, layout, resource or hardware predicate is unknown. It is never silently
used as a complete-transform fallback for a request that asks for native
per-stage FP16 rounding.

## Validation and calibration

`benchmarks/hadacore` retains the complete-transform comparator through
`hadacore_execute`. The separate local ABI is generated by
`scripts/hadacore_tile_provider.py`. It extracts the hash-pinned device
arithmetic into a block-relative transform, accepts packed tile groups and an
explicit stream, and reuses one shared scratch region across a requested number
of groups. Final output scaling is fused into the stores. Increasing
`groups_per_block` changes sequential reuse within a block; it does not add
another butterfly stage or imply overlapping stage execution.

Set `CUDA_HOME` to the target toolkit before building (CUDA 12.8 on PRO6000).
Both the comparator and tile builder emit SM80 native code and compute80 PTX.
The PTX can be JIT-compiled on a newer target, but Blackwell compatibility and
numerical behavior remain unvalidated until the target validation below passes.
Do not reuse A100 profiles: regenerate local/native measurements and public
AUTO validation on the selected GPU with the same main library and profile
environment. See the [target extension workflow](benchmarks/external-extensions.md#target-host-fft17-and-optional-mma9).

Preparation and compilation run without a GPU. The generated build records its
sources, compiler, license and binary hashes. GPU validation checks complete
outputs against the pinned upstream algorithm, records separate errors against
the CPU FP16 radix-2 reference, and tests buffer guards, input preservation,
repeated execution and CUDA Graph replay. Different rounding contracts are
reported explicitly. No floating-point threshold is silently relaxed.

```bash
python scripts/hadacore_tile_provider.py --upstream external/hadacore \
  --output build/hadacore-tile --nvcc "$CUDA_HOME/bin/nvcc"
python scripts/validate_hadacore_tile.py --prepare --full \
  --build build/hadacore-tile --output results/hadacore-validation \
  --gpu-uuid 'GPU-<target-uuid>'
python scripts/calibrate_hadacore_tile.py --execute \
  --build build/hadacore-tile --output results/hadacore-validation \
  --upstream-library build/hadacore/libhadacore_baseline.so \
  --profile results/hadacore-validation/profile.json
```

The bounded population covers lengths 2 through 32768 and batches 1, 2, 4, 16,
64 and 256. Requests that cannot fill a complete group are recorded as provider
limitations; neither padding nor batch reduction is implicit. Each legal
request measures group reuse counts 1, 2 and 4. Runtime resource queries record
registers, shared and local storage, launch limits and occupancy capacity.
Compilation, allocation, plan preparation and CPU checking stay outside timing.

## Public selection contract

`ArithmeticPolicy.STRICT` preserves existing arithmetic. The explicit
`ArithmeticPolicy.ALLOW_FP16_MMA` option permits validated MMA candidates
alongside native candidates. The initial local lowering covers forward,
out-of-place, packed natural-order, rank-one FP16 FWHT. Arbitrary stride,
multi-stage MMA composition and other directions need their own lowering and
validation; a packed tile ABI alone does not establish those capabilities.

Target-local profiles bind each candidate to its GPU, binary, launch geometry,
validation evidence and complete-call timing protocol. A native endpoint must
be measured through the same public interface and protocol before AUTO compares
the two. Missing paired calibration retains native selection and explains the
missing MMA coverage. An explicit MMA replay requires matching evidence.
Runtime `MEASURE` with this new arithmetic option is currently rejected: the
legacy online verifier assumes stage rounding and is not its numerical oracle.

`scripts/calibrate_hadacore_native.py` collects the corresponding STRICT public
endpoints. `scripts/validate_hadacore_public.py` checks the resulting public AUTO
selection and independently measures it. A local-provider benchmark does not
replace this final public-path check. Profiles contain measured requests only;
they do not claim interpolation or global optimality for unseen shapes.

After activating the target's ordinary cuButterfly profile environment, collect
the native controls and assemble the paired selection profile:

```bash
python scripts/calibrate_hadacore_native.py --execute \
  --prepared results/hadacore-validation --output results/hadacore-native \
  --library build/libcuntt.so
python scripts/calibrate_hadacore_native.py --export-only \
  --prepared results/hadacore-validation --output results/hadacore-native \
  --library build/libcuntt.so --profile results/hadacore-native/profile.json
python scripts/calibrate_hadacore_tile.py --export-only \
  --build build/hadacore-tile --output results/hadacore-validation \
  --native-profile results/hadacore-native/profile.json \
  --profile results/hadacore-validation/profile.json
python scripts/validate_hadacore_public.py --execute \
  --prepared results/hadacore-validation --output results/hadacore-public \
  --library build/libcuntt.so --profile results/hadacore-validation/profile.json
export CUBUTTERFLY_HADACORE_PROFILE="$PWD/results/hadacore-validation/profile.json"
```

Use the same main library for native calibration and public validation. In
Python, pass `arithmetic_policy=cubutterfly.ArithmeticPolicy.ALLOW_FP16_MMA`
to the ordinary `cubutterfly.Transform`. Plan construction reads the saved
profile; execution does not repeat calibration or compile a kernel.

Once local-core measurements exist, the remaining stages also have a resumable
entry point:

```bash
python scripts/complete_hadacore_calibration.py --execute \
  --prepared results/hadacore-validation --build build/hadacore-tile \
  --library build/libcuntt.so --native-output results/hadacore-native \
  --public-output results/hadacore-public \
  --profile results/hadacore-validation/profile.json
```

This runs native controls, validates the paired profile and checks public
selection in order. A failed stage stops the workflow and retains its evidence;
successful matching measurements are reused.
