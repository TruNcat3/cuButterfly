# PRO6000 research handoff, November 7

This snapshot carries the current cuButterfly source, bounded A100 evidence,
and the migration entry for RTX PRO 6000 Blackwell Server Edition 96GB.
It is a research handoff, not a measured Blackwell release.

## Start on the target host

Update a clean checkout of `main` using `git pull --ff-only`, or clone
`https://github.com/TruNcat3/cuButterfly.git`. Record `git rev-parse HEAD` with
the target experiments. Follow the [platform runbook](hardware/pro6000_server96.md)
for the separate Conda environment, CUDA/MathDx/Torch prerequisites and external
baselines. Existing A100 calibration and compiled modules are not target inputs.

The entry is `scripts/research_platform.py`, with stages `plan`, `doctor`,
`build`, `prepare`, `run`, and `report`. Compilation and CPU reference preparation
precede GPU calibration and measurement. The [scope contract](../config/paper_portability/README.md)
freezes **quick12** as a subset of **full66**; full is the main operator population,
not all paper experiments. Cyclic NTT, FP16, mechanisms and applications retain
their own configurations and should follow the main target acceptance.

The target build is SM120. CUDA 12.8 or later, compatible MathDx and a Torch
wheel containing SM120 code must pass the actual compile/preflight checks.
Target GPU execution remains untested here. Use local SSD or NAS for preparation
and output; do not use `/sdb` or `/mnt/sdb`.

## Experiment snapshots

Operator, FP16 and application summaries are stored under
`experiments/snapshots/`. The software repository contains experiment runners
and reproducible report inputs; manuscript sources and PDFs are maintained
separately. Use `python scripts/render_readme_performance.py` and
`python scripts/render_cpu_normalized_performance.py` to redraw public summaries.
Original measurement paths and hashes remain provenance; raw campaigns need
not be present in a source checkout. Historical and current repetitions retain
separate populations, and missing results are not imputed.

The [QuaRot audit](quarot_attribution_20261107.md) explains why its actual
FP16-storage/FP32-compute, 32/64-point requests cannot inherit the main FP32 FWHT
mean. The eight-request diagnostic is prepared in
[`configs/experiments/quarot_contracts_20261107.json`](../configs/experiments/quarot_contracts_20261107.json).
Its timings exclude the rest of the model, so they cannot replace full-model
end-to-end records. Follow-up numerical checks report errors against CPU FP32
with final FP16 storage, without an unapproved acceptance threshold.

## Validation boundary

The publication checkout passes 351 focused CPU tests for target migration,
source packaging, compilation requests, frozen paper data and QuaRot diagnostic
contracts, plus 11 tests for explicitly recorded local-only artifact links. Quick/full plans preserve 12/66 requests and separate target-local
calibration. The added template dependencies exist and no merge markers remain.
Manuscript build validation is separate from this software checkout.

These checks do not certify target GPU correctness, target speed, all historical
experiment scripts, or unseen-request cost-model ranking. Installation and
measured target calibration must precede the PRO6000 comparison. See the
[A100 status](research_status_20261107.md) for the completed bounded populations
and the remaining FP16, calibration-generalization and application limitations.

The original raw campaigns remain on the research host. The source-release
[artifact manifest](../config/repository_local_artifacts.json) records exact
local-only paths; ordinary repository checks report missing archived artifacts
separately, while `python scripts/check_repository.py --strict-local-artifacts`
requires all of them. A successful source check does not validate absent raw data.
