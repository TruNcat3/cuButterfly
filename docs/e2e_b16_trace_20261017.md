# 2048², batch 16 xD trace

> **Report ID:** `e2e-poisson-2048-b16-adaptive-20261017`  
> **Status:** `measured` endpoint plus `diagnostic` trace  
> **Owner:** cuButterfly research artifact; software attribution is maintained in
> [Project and authors](about.md)  
> **Scope:** A100 80GB PCIe, CUDA 12.4, FP32, rank-2 periodic spectral Poisson solve

## Scope and question

This trace isolates the large-batch endpoint that previously fell behind the
reference libraries. It asks whether the complete xD selector can measure and
reuse fused axis plans when the B16 input/output boundary is larger than the
old fixed tuning budget. Every run used the same FP32 periodic spectral Poisson
inputs, A100 80GB GPU UUID `GPU-0eae5f07-33de-321b-70a9-ffeae49309e6`, and
the complete Graph boundary. The application is a 2D FFT-based Poisson solve,
not a standalone 1D FFT claim.

| Field | Value |
|---|---|
| Workload | `-Laplacian(u)=f` on `[0,2π)^2`, mean-zero solution |
| Shape / batch | `2048 x 2048`, `B=16` |
| Precision / norm | FP32, backward FFT normalization |
| Input policy | deterministic seed `20261013`; CPU mean-zero projection |
| Timing boundary | device input copy + complete RHS FFT/multiplier/inverse FFT + output copy + synchronization |
| Excluded | setup, compilation, plan/search, Graph capture and warmup |
| Baselines | PyTorch CUDA Graph and CuPy CUDA Graph, same inputs and boundary |
| Correctness | finite outputs, retention and same-backend checks; full error distributions retained |

The result is a separate application cohort. It must not be appended to the
nine-point image-filter cohort or used to rewrite its negative cases.
The repaired adaptive result is registered as the independent
`end_to_end_fft_poisson_adaptive_revision` supplement in the benchmark scope;
its machine-readable manifest is
[`manifest.json`](../results/e2e_current_20261017/poisson_2048_b16_adaptive_trace/manifest.json).

## Protocol and selection diagnosis

The original run used build
`2ba90a76d65770eb70629279c27f7495d72b883537e08ea49e37944210988aff` with the
unset-budget behavior that was then fixed. It selected the static packed-axis
fallback because the default 512 MiB tuning bound rejected the complete
candidate set. The B16 input/output boundary is 268.7 MiB, and the forward and
inverse temporary workspaces are 537.4 MiB and 806.1 MiB respectively. The
selection was therefore not evidence that no fused candidate existed.

| B16 plan | status / selection | fused axes | launches | workspace | Graph time |
| --- | --- | ---: | ---: | ---: | ---: |
| Original default | `diagnostic`, `static_model`, packed axes | no | 4 + 5 | 537.4 / 806.1 MiB | 4.270 ms |
| Explicit 2 GiB tuning | `measured`, VkFFT / cuFFTDx | yes | 2 + 2 | 268.7 / 537.4 MiB | 3.079 ms |
| Adaptive default after fix | `measured`, VkFFT / cuFFTDx | yes | 2 + 2 | 268.7 / 537.4 MiB | 3.098 ms |

The original kernel trace contains 12 kernels. Four serialized
`tiled_transpose_2d_kernel` launches account for 1.373 ms, and the separate
real-output scale kernel accounts for another 0.364 ms. The fused adaptive
trace contains seven kernels, with one VkFFT axis kernel and one cuFFTDx axis
kernel; it has no permutation or separate scale kernel. Kernel busy time falls
from 3.530 ms to 2.393 ms. The remaining wall time is the common boundary,
frequency-domain multiply and kernel submission overhead, rather than an
unaccounted compile or Python path.

## Current-build Torch-only control

The current contract build was independently rerun with the PyTorch/cuFFT
backend and the cuButterfly Torch adapter. This control uses the same Graph
boundary, includes device input refresh and output clone, and excludes plan
construction, search and capture from steady-state timing. CuPy was not needed
for this control, which makes it runnable in the pinned PyTorch environment.

| 1024² / B=16 | 0.7484 ms | 0.8943 ms | 0.7521 ms | 0.9004 ms | 1.197× |
| 2048² / B=4 | 1.8421 ms | 0.9869 ms | 0.8523 ms | 0.9880 ms | 1.159× |
| 2048² / B=16 | 3.4899 ms | 3.5723 ms | 3.0396 ms | 3.5789 ms | 1.177× |

The reports are [`1024²`](../results/e2e_current_20261017/poisson_1024_b16_torch_v2/report.json)
and [`2048²`](../results/e2e_current_20261017/poisson_2048_b16_torch_v2/report.json),
with the B4 control in [`2048²/B4`](../results/e2e_current_20261017/poisson_2048_b4_torch_v2/report.json).
All outputs were finite and independently allocated. Relative L2 error against
the CPU FP32 reference was 4.14e-7--5.82e-7. These rows extend the current-build
evidence; they do not replace the separate CuPy-inclusive cohort above.
The B4 report uses eight timed calls and the cache-bump B16 report uses four;
both retain the same warmup, stream, and complete-call boundary, so the rows
are a diagnostic control rather than a pooled confidence interval.

The fresh plan metadata also records the selection gate. For the 2048²/B16
forward plan it reports 29 generated choices, 25 executable candidates and 52
complete-plan measurements after axis refinement. The inverse plan reports 47
executable candidates and 72 measurements. The tuning gate fit within a 2 GiB
bounded budget and the available A100 memory. This is the same complete-plan
search path for B4 and B16; the B4 eager deficit therefore belongs to the call
submission boundary, not to an unsearched fixed design point.

## Attribution and limitation

The bounded fix is in [`src/c_api.cpp`](../src/c_api.cpp#L1740): when the
environment variable is unset, the tuning bound is
`max(512 MiB, min(2 GiB, free_VRAM / 4))`. The existing `free_VRAM / 2`
allocation guard and explicit `CUBUTTERFLY_XD_TUNE_MAX_BYTES` override remain
unchanged. Thus an idle A100 automatically measures the complete B16 candidate
set, while a busy or small-memory GPU still retains an executable fallback. The
compact-real cache generation is also bumped when this gate changes, so an old
static packed mapping cannot silently bypass the new search.

The trace explains a selection-budget failure and its engineering repair. It
does not establish that every 2D or 3D size will select the same pair of cores,
nor that setup/search cost is free for a first invocation. Those costs are
reported separately and excluded from the steady-state complete-call result.
