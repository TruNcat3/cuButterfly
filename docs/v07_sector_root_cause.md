# v0.7 Global-Load Sector Root-Cause Audit

## Why Similar Dataflow Does Not Imply Similar Sector Counts

The current matched V100 capture compares v0.6 with the v0.7 dual-warp128
vector-radix4 depth-6 point at uint32 `logN=20`, batch 16. DRAM reads differ
by only 3.1% and global-store sectors by 0.6%, but v0.7 executes 32.2% more
global-load sectors:

| metric | v0.6 | v0.7 d6 | v0.7/v0.6 |
|:--|--:|--:|--:|
| kernel time (us) | 1259.0 | 1345.7 | 1.069x |
| DRAM read (MiB) | 268.5 | 276.8 | 1.031x |
| global-load sectors | 29,851,046 | 39,449,055 | 1.322x |
| global-store sectors | 8,388,611 | 8,337,912 | 0.994x |
| active warps (%) | 47.75 | 24.67 | 0.517x |

`global-load sectors` counts cache requests generated by load instructions. It
does not count unique bytes eventually fetched from DRAM. Requests issued by
different warp instructions cannot be coalesced retroactively, even when they
hit the same cache line. The external dataflow can therefore be identical
while the physical coefficient request stream differs substantially.

## Stage Model

The run contains 32,768 producer/consumer 1024-point row transforms. A static
warp-address model predicts 576 coefficient sectors per row for v0.6 and 912
for v0.7 d6. Including the common data requests, this predicts an 11,010,048
sector gap; the refreshed NCU pass measures 9,598,009, so the model explains
87.2% of the delta.

The dominant v0.7 term is stage 6. Depth 6 means `stage < 6`, so stage 6 still
uses the direct vector path. Each lane owns four consecutive values. Its four
coefficient instructions each activate half a warp with a 16-byte address
stride, producing about 512 sectors per row. This is a physical-codelet layout
effect, not a change to the NTT graph or external boundary.

The already measured depth differences validate the model independently:

| newly distributed stage | measured sector reduction | predicted | ratio |
|--:|--:|--:|--:|
| 2 | 1,344,727 | 1,572,864 | 0.855x |
| 3 | 1,977,590 | 1,572,864 | 1.257x |
| 4 | 3,208,643 | 3,145,728 | 1.020x |
| 5 | 7,239,982 | 6,291,456 | 1.151x |

The growth with stage depth follows the wider coefficient footprint. Replay
and readiness variation move individual deltas, but not their direction or
order of magnitude.

views of each SASS PC, SourceCounters gives:

| implementation | source category | theoretical sectors |
|:--|:--|--:|
| v0.6 | external data | 6,291,456 |
| v0.6 | coefficients | 23,855,104 |
| v0.7 d6 | external data | 6,291,456 |
| v0.7 d6 | stage 0-1 coefficients | 1,572,864 |
| v0.7 d6 | stage 2-6 coefficients | 23,330,816 |
| v0.7 d6 | stage 7-9 coefficients | 7,118,848 |

The external-data sector count is exactly identical. Source theoretical totals
close to `1.012x` and `1.041x` of the v0.6/v0.7 aggregate L1TEX counters; this
small mismatch is expected because SourceCounters reports theoretical L2
transactions rather than the aggregate L1TEX counter. Classification covers
100% of v0.6 and 95.27% of v0.7 sectors. The remaining 4.73% is retained by PC
in `source_pc_attribution.csv` rather than assigned speculatively.

## What Is Actually Pipelined

The current v0.7 kernel keeps two independent warp128 groups resident, but a
group still executes:

```text
packet load -> barrier -> row 0 complete NTT -> row 1 complete NTT
            -> row 2 complete NTT -> row 3 complete NTT -> packet store
```

The groups can interleave through ordinary warp scheduling. The code does not
yet overlap different row tokens across load, prefix, tail, and store phases.
At the same time, v0.7 uses 106 registers/thread and 41,184 shared bytes/CTA,
limiting V100 residency to two CTAs or 16 warps/SM. V0.6 uses 40 registers and
16,416 shared bytes, allowing four CTAs or 32 warps/SM. The current resident
subgraph therefore has less hardware latency-hiding capacity than v0.6.

## Stage-6 Distribution Candidate

The vector-radix4 design space now accepts `coefficient_reuse_stages=7`. Its
stage-6 codelet distributes the 64 coefficients as even/odd pairs across 32
lanes and selects each pair member before one warp shuffle. This reduces the
number of fragmented slot-wise loads without the two-shuffle-per-slot cost of
the initial low/high-bank prototype. The specialized-kernel selector is
covered by a regression test so depth 7 cannot silently fall back to the
generic hierarchical kernel.

On V100, the final d7 cubin uses 105 registers/thread versus d6's 106, so both
retain the same two-CTA residency limit. A 100-repeat CUDA-event check at
`logN=20`, batch 16 measured 1.321 ms for d6 and 1.349 ms for d7.

The controlled NCU capture then measured 39,999,693 global-load sectors for d6
and 31,432,704 for d7. The 8,566,989-sector reduction is 1.021x the static
8,388,608 prediction and removes 83.7% of d6's excess over v0.6. The model is
therefore validated. D7 nevertheless takes 1.008x d6 time because warp
instructions rise 1.011x and MIO throttle stall rises 1.137x; lower long
scoreboard stall does not repay the shuffle/issue cost.

D7 remains an experimental candidate rather than the default. Its follow-up is
now implemented as the separate
`homogeneous-warp128-vector-radix4-packed-stage6-static-io` physical core. The
plan appends a 16-byte-aligned side table containing the producer's 64 stage-6
coefficients and 64 coefficients for each of the 1024 consumer rows. This is a
one-time plan construction cost; execution adds no preprocessing launch and no
workspace traffic.

The generated SM70 code contains paired `LDG.E.128.SYS` instructions for the
coefficient and Shoup vectors in both producer and consumer paths. It uses 98
registers/thread, versus 106 for d6 and 105 for d7, with zero local allocation.
A same-session, unlocked-clock 100-repeat screen measured 1.360 ms for d6,
1.240 ms for d7, and 1.273 ms for packed stage6. This establishes that vector
loading recovers d6's issue cost but does not yet establish a fixed-clock win
over d7.

The fixed-clock capture confirms the distinction. Vector16 reduces d7's
31.34M global-load sectors to 26.73M and registers/thread from 105 to 98, but
time rises from 1339.6 us to 1434.2 us. Its long-scoreboard stall rises from
17.23% to 21.94%. The aligned table is effective; concentrating each 64-word
request into sixteen `LDG.128` lanes reduces memory-level parallelism and makes
all four register slots wait on the same wide load.

The follow-up
`homogeneous-warp128-vector-radix4-packed-stage6-distributed-static-io` core
keeps the same side table but assigns one adjacent coefficient pair to each of
32 lanes. SM70 SASS contains `LDG.E.64.SYS`; the kernel uses 109
registers/thread, zero local allocation, and retains two CTAs/SM. A same-session
50-repeat screen measures 1.191 ms, versus 1.245 ms for d7 and 1.274 ms for
vector16. This is a 4.3% event-time improvement over d7. Fixed-clock counters
are still required before selector promotion.

Collect that controlled decision with:


The script profiles only v0.6, d6, and d7, then writes `summary.csv` and an
automatic sector/time/instruction decision to
`results/ncu_vector_stage6_distribution/analysis.md`. A genuine row-token

The fixed-clock five-way decision is collected with:

It compares v0.6, d6, d7, packed vector16, and packed lane32. Cache state is

That capture measures lane32 at 1336.3 us, 0.5% faster than d7 but 6.65% slower
than v0.6. Lane32 preserves vector16's 26.36M load sectors while reducing

therefore validated, but v0.6 still wins through 31.2% fewer warp instructions

## Dynamic Instruction Closure And Packet Core

SourceCounters closes the remaining instruction gap. After deduplicating SASS
PCs across inline-stack views, v0.7 d6 executes 60.45M more warp instructions
than v0.6. `SHFL` contributes 21.49M; control contributes 23.06M, including
17.60M from `BSYNC/BSSY/BMOV`; `SEL+ISETP` contributes another 22.45M. Global
memory instructions are slightly lower and shared-memory instructions are
5.01M lower. The deficit is therefore the per-row warp-register organization,
not extra NTT arithmetic or an extra external state. The full table is in
`results/ncu_v07_sector_attribution/instruction_attribution.md`.

The new
`homogeneous-warp128-packet-shared-radix4-static-io` core targets that result
directly. Four rows form one 128-thread packet and execute five shared
radix-4 stage pairs, with one named barrier per pair. A 256-thread CTA may hold
two independent packets, so the v0.7 subgraph schedule is preserved while the
physical unit reuses v0.6's low-instruction arithmetic organization. The
128-thread cubin uses 80 registers/thread; the dual-packet version uses 72.

A same-session event screen at uint32 `logN=20`, batch 16 measures 1.073 ms for
packet128, 1.341 ms for lane32, and 1.583 ms for v0.6. A 100-repeat role scan
selects `9:11` at 1.097 ms. This is promising but not a fixed-clock claim.
Five packet128 CTAs/SM can violate forward progress when persistent consumers
occupy the fifth residency slot, so the plan caps this core at four CTAs/SM.
Confirm time and instruction-pipe reductions with:

```bash
sudo -E ./scripts/profile_packet_shared_radix4_ncu.sh
```

The fixed-clock capture closes that decision: packet128 takes 1061.2 us at
batch 16, versus 1259.5 us for v0.6 and 1342.1 us for lane32. It executes
172.47M warp instructions, 5.2% fewer than v0.6 and 27.5% fewer than lane32.
The physical codelet is therefore no longer the dominant v0.7 deficit.

## Packet-Granular Online Handoff

The original packet core still used one readiness counter per transform. A
consumer waited for all 1024 producer rows before loading its four-row packet,
so the kernel overlapped roles only across transforms. The online option uses
the consumer mapping's `token_interleave` as a q-wave width in `{4,8,16}`.
Zero preserves the aggregate barrier. A wave contains 64 words per q-group,
so the 1024-word staging tile imposes a hard maximum width of 16.

For a nonzero wave, the producer publishes each four-row packet with a release
store after its boundary writes complete. The consumer acquires the four
quadrant packets required by each dependency-closed radix-4 unit. It then
loads the wave once through a coalesced 4-KiB staging tile, evaluates stages
0-1 immediately, and keeps the partial state on chip for stages 2-9. Boundary
traffic remains one write and one read per element.

Forward and inverse verification pass for every wave width. The first
packet-flag NCU capture was 5.6% slower at batch 16 and 2.4% slower at batch
32. It generated about 16% more global-load sectors and 26-58% more CBU
instructions, exposing both a wave-load mapping problem and repeated polling.
That before-control remains in `results/ncu_packet_streaming/`.
Coalesced staging removes the known wave-load mapping error. A later
q-frontier experiment tried to replace the four packet tokens with one merged
counter. Its fixed-clock capture reduced CBU pressure, but subsequent clean
builds exposed a producer-order race in both forward and inverse verification.
The q-frontier protocol is therefore rejected; its measurements are retained
only as synchronization-attribution evidence and are not selector-eligible.
The supported online path keeps per-packet release/acquire visibility.

An earlier wave-32 event screen appeared to cross the aggregate path at batch
64. That result was invalid: 32 q-groups require 2048 staging words, while the
resident tile contains 1024. The out-of-bounds shared-memory access corrupted
the result. The plan now rejects wave 32 and the device helper independently
caps the width at the staging capacity.

The corrected V100 screen uses wave 16, three order-rotated independent
processes, ten warmups, and 50 timed iterations per process:

| batch | v0.6 (ms) | v0.7 aggregate (ms) | v0.7 online (ms) | aggregate/v0.6 | online/v0.6 | online/aggregate |
|---:|---:|---:|---:|---:|---:|---:|
| 16 | 1.460 | 1.082 | 1.130 | 1.350x | 1.292x | 0.957x |
| 32 | 4.113 | 2.418 | 2.502 | 1.701x | 1.644x | 0.966x |
| 64 | 9.128 | 4.931 | 5.138 | 1.851x | 1.777x | 0.960x |

Aggregate and online reach 1.620x and 1.557x geomean throughput relative to
v0.6. Online remains about 4% below aggregate across this batch set. Larger
batch is not the same as a longer per-transform subgraph stream: the aggregate
path already pipelines complete transforms. Length scaling therefore requires
a parameterized decomposition beyond the current fixed `10+10` instance.

The corrected wave-16 NCU capture measures online/aggregate time at 0.986x for
batch 16 and 1.080x for batch 32. Online increases warp instructions by
10.2-11.6%, global-load sectors by 8.8-9.6%, shared-load conflicts by
24.1-24.3%, and CBU instructions by 25.0-30.0%. Barrier stall falls because
the aggregate transform barrier is removed, but the saved wait is exchanged
for readiness loads, shared staging conflicts, and long-scoreboard latency.
This is the remaining online orchestration tax.

## Staging Row Padding

The first controlled follow-up changes the wave-16 staging row stride from 256
to 257 words. This breaks the identical shared-bank phase of the four writer
rows while adding only four words (16 bytes) per CTA, so the V100 residency
target remains four CTAs/SM. The pre-padding event and NCU results are retained
in `results/packet_streaming_v06_comparison/before_padding_*` and
`results/ncu_packet_streaming_staged_packet_flags/`.

The three-process event screen is neutral to slightly negative: online changes
by +1.3%, +0.9%, and -0.2% at batch 16, 32, and 64. Therefore padding remains a
candidate rather than a promoted default. Its dedicated fixed-clock capture is
written to `results/ncu_packet_streaming_padded_staging/`; promotion requires a
material shared-load-conflict reduction without a kernel-time regression.

The fixed-clock capture rejects the candidate. Online shared-load conflicts
increase by 0.6-0.7%, registers rise from 64 to 71 per thread, and batch-16/32
online time changes by +2.4%/+0.4%. The implementation is reverted. The next
candidate exposes acquire-poll backoff through `ready_window`: values
`1/2/4/8/16` correspond to 32/64/128/256/512 sleep cycles, with `2` preserving
the previous default. The event screen selects `4/2/16` for batch `16/32/64`.
Those points reach 0.954x/0.965x/0.967x of aggregate throughput, so polling
frequency explains less than one percent of performance and is not the
remaining primary bottleneck. The fixed-clock follow-up is written to
`results/ncu_packet_polling_backoff/`.

The next identity-preserving protocol packs the 256 packet flags into eight
32-bit words. Producers publish their unique bit with a release `fetch_or`;
consumers acquire four quadrant masks per q-wave. Unlike the rejected
q-frontier count, completion of a mask proves that every required packet has
published. The event screen selects bitmap `ready_window=16/8/8` for batch
16/32/64. It is neutral at batch 16, improves batch 32/64 by 3.2% over
per-packet readiness, and reaches 0.992x/0.990x aggregate throughput at the two
larger batches. Fixed-clock attribution is collected under
`results/ncu_packet_readiness_modes/`.

That attribution shows only a 0.6%-0.7% bitmap reduction in load sectors and
no reduction in shared-load conflicts. Its batch-16/32 replay gain instead
tracks 6.4%/11.0% fewer CBU instructions. Readiness metadata therefore
explains control overhead but not the remaining online sector/conflict excess.
The stage-0/1 implementation mixes four writer rows in each warp, whereas the
aggregate path groups work by row. `packet_compute_layout=warp-rows` exposes a
controlled remapping intended to restore coefficient broadcast and shared-bank
phase locality. Its event screen is neutral to slightly negative at batch
32/64, so `results/ncu_packet_compute_layout/` is required before deciding
whether the predicted counter reduction exists but is latency-irrelevant, or
whether the source-level bank model is incomplete.

The fixed-clock capture resolves that question. Relative to bitmap
interleaved rows, warp rows reduce global-load sectors by 8.7%-8.8%, shared
load conflicts by 18.9%-19.2%, warp instructions by about 1%, and LSU
instructions by 1.6%-2.1%. The mapping model is therefore correct. Replay time
improves 2.1%/4.4% at batch 16/32 but regresses 2.2% at batch 64, while warm
CUDA-event timing remains the promotion authority. The removed traffic is
largely cache-resident or hidden behind other work rather than the steady-state
critical path.

A complete producer-weight scan confirms that this is not a stale service
ratio. Warp rows select `8:12` at batch 16 and the existing `5:15` at batch
32/64. They reach 0.965x/0.987x/0.982x aggregate throughput; giving the
producer more CTAs sharply degrades the longer streams. Pipeline timestamps
show only a 60-70 us consumer tail at batch 32, so the roles are already close
to balanced.

The packet helper originally executed three barriers per q-wave: readiness,
staging, and post-compute. `packet_fold_wave_barriers` removes the post-compute
barrier because the next readiness/staging barrier also protects shared-memory
reuse, while retaining one final barrier. Forward and inverse checks pass over
repeated plan execution. Three-process event medians change by at most 0.6%
and the best online points reach 0.967x/0.989x/0.992x aggregate throughput.
This rejects redundant synchronization as the remaining explanation.

Finally, batch 1/2/4/8 spot checks do not reveal an unamortized-fill crossover:
online/aggregate throughput is 0.986x/0.964x/0.938x/0.923x with equal service
weights. Aggregate already distributes complete transforms across resident
CTAs; online publication adds protocol work even before a long batch reaches
steady state. The next architectural experiment must therefore generate more
than two homogeneous subgraphs per transform and test whether a longer
dependency stream amortizes protocol work. Further tuning of the fixed
`10+10` pair is no longer the primary path.
