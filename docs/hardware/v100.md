# V100：同步源码后进行本机校准与综合实验

这个入口供另一台机器独立运行。默认目标为 SM70，GPU 的型号、显存、UUID 和驱动在执行时检测；V100 PCIe/SXM、16GB/32GB 使用不同结果目录和校准身份。当前交付是可运行的实验准备包，不包含新版本 V100 性能结论。

本次版本包含运行所需的源码、脚本和实验矩阵，可在另一台机器执行 `git pull --ff-only origin main` 更新。也可以运行 `python scripts/package_research_source.py --output /path/to/cuButterfly-v100-source.tar.gz` 生成迁移包；它包含工作区中的源码与矩阵，附逐文件 SHA256 manifest 与归档校验和。后续若有尚未提交的开发内容，使用这个入口可避免 `git archive HEAD` 遗漏工作区修改。

## 1. 环境和依赖

在同步后的仓库根目录运行。复用目标机已有 `cubutterfly` conda 环境；没有时创建一次：

```bash
conda create -n cubutterfly python=3.11 pip -y
conda activate cubutterfly
python -m pip install 'numpy<2' pytest 'cmake>=3.26'
bash scripts/install_cufftdx.sh
bash scripts/install_vkfft.sh
```

准备本轮使用的 CUDA 12.4 工具链，并确保主机编译器与其兼容。MathDx 与 VkFFT 由现有安装脚本固定依赖版本；构建脚本本身不隐式下载它们。顶层 CMake 首次会获取 nlohmann/json 3.11.3；离线时传 `--json-root` 指向已有的对应源码目录。源码包不包含 CUDA、外部库或 A100 二进制。

构建目前仍需要已跟踪的 `results/v100_scaling_full_summary.csv` 生成 legacy selector header；源码包只额外保留这一份真实历史构建输入。它不进入本轮校准 profile，也不能作为新 V100 测量证据；入口会重新校准、搜索和计时，其他历史结果不随包复制。

准备脚本还会生成本地 architecture manifest，把历史 `results/` 路径标为生成物，而非源码依赖。因此不需要复制 A100 校准目录或伪造空的硬件 profile。

Dao FWHT 是可选外部基线，需要带 CUDA 的 PyTorch。本机 A100 实验使用 PyTorch 2.5.1、NumPy 1.26.4、fast-hadamard-transform 1.1.0。目标机可使用同版本，并运行现有的 SM70 补丁安装入口：

```bash
python -m pip install torch==2.5.1 --index-url https://download.pytorch.org/whl/cu124
CUDA_HOME=/usr/local/cuda-12.4 PYTHON="$(command -v python)" \
  bash scripts/install_external_fht.sh
```

注意：这个已有的 Dao 安装入口最后会查询一次 GPU，适合在 V100 已可用时执行。它不运行性能矩阵。BF16 在 V100 上按软件舍入/模拟语义记录，不能称为原生 BF16 吞吐；没有匹配的外部基线时会明确列出缺测。

## 2. 先做 CPU 构建和有限预编译

这两步可在 GPU 忙时运行；显式指定 SM70，并隐藏 CUDA 设备。它们不会安装覆盖其他环境，也不会改变 A100 队列。

```bash
bash scripts/prepare_research_target.sh \
  --build-dir build-v100-sm70 --cuda-arch 70 --jobs 2 \
  --nvcc /usr/local/cuda-12.4/bin/nvcc \
  --python "$(command -v python)" --with-vkfft

python scripts/run_research_target.py --mode precompile \
  --build-dir build-v100-sm70 --cuda-arch 70 --jobs 2 \
  --nvcc /usr/local/cuda-12.4/bin/nvcc \
  --output-dir results/v100-current
```

主库和测试程序位于 `build-v100-sm70`，组合 NTT 测试程序位于 `build-v100-sm70/crypto-ntt-sm70`。`ctest -N` 只列举测试，不代表 GPU 测试通过。按需加 `--install --prefix "$CONDA_PREFIX"` 可安装到该统一环境；研究 runner 直接使用显式构建目录，不依赖旧的已安装库。

预编译覆盖已知 mapping proposals 和 28 个校准基点的模板请求，不导入历史计时，也不表示这些 mapping 在 V100 上合法或最优。公共搜索仍可能发现新模板并现场编译；所有编译、plan 初始化和 CPU 核验都在 kernel 计时之外。

GPU-NTT 的历史比较适配器只覆盖固定模数的 word64 正向循环 NTT。要保留这组对比，使用相同版本重新编译，不能复制 A100 可执行文件：

```bash
git clone https://github.com/Alisah-Ozcan/GPU-NTT.git external/GPU-NTT
git -C external/GPU-NTT checkout --detach d03c5eaeadaa780d153496afcb3b6a9b79a13a63
CUDA_VISIBLE_DEVICES= cmake -S external/GPU-NTT -B build-v100-gpuntt \
  -DCMAKE_CUDA_ARCHITECTURES=70 -DCMAKE_BUILD_TYPE=Release \
  -DCMAKE_CUDA_COMPILER=/usr/local/cuda-12.4/bin/nvcc
CUDA_VISIBLE_DEVICES= cmake --build build-v100-gpuntt --parallel 2
CUDA_VISIBLE_DEVICES= /usr/local/cuda-12.4/bin/nvcc -std=c++17 -O3 -arch=sm_70 \
  -I external/GPU-NTT/src/include benchmarks/gpuntt_merge_gap_bench.cu \
  build-v100-gpuntt/src/libntt-1.0.a -o build-v100-sm70/gpuntt_merge_gap_bench
```

## 3. 在空闲 V100 上执行

先用 `nvidia-smi -L` 找到目标 UUID，替换下面的 `GPU-...`。下面包含可选的 Dao 和 GPU-NTT 基线；未准备的基线删除对应参数即可，其缺失会记录为 unavailable。

```bash
python scripts/run_research_target.py --mode run \
  --gpu GPU-... --cuda-arch 70 --build-dir build-v100-sm70 \
  --nvcc /usr/local/cuda-12.4/bin/nvcc \
  --output-dir results/v100-current --resume \
  --fht-python "$(command -v python)" \
  --gpuntt-binary build-v100-sm70/gpuntt_merge_gap_bench
```

入口先测硬件能力、调度/流水开销及 28 个 shared-iterative 基点的独立 stage 曲线。只有声明的基点通过验证，才进入综合对比；确认候选缺少的 stage 服务由原有搜索入口继续采样。该有限基点校准与候选覆盖状态分开报告，不宣称一次采样覆盖无限设计空间。

| 顺序 | 配置数 | 范围 |
| --- | ---: | --- |
| core | 74 | 与 A100 原始矩阵一致 |
| batch_precision | 284 | 大 batch、精度、逆运算扩展 |
| crypto | 208 | 多模数位宽、非规则 batch、正逆循环 NTT |
| operator_extensions | 18 | FWHT、zeta/Mobius、structured 逆运算及部分 stride |
| composed | 138 | negacyclic/coset、RNS、多方向及边界输入 |
| plans | 16 | 完整核验的二维/任意长度 FFT，与 cuFFT 比较 |

共 738 个配置；其中 704 个来自原有实验，operator_extensions 和 plans 新增非密码学配置合计 34 个。组合实验的 24 个前置正确性检查不另计为性能配置。另有 11 个二维非 FFT、embedding 等场景因现有 plan 测试工具没有完整输出核验而延期，详见 [应用覆盖路线图](../application_coverage_roadmap.md)。

任意长度 FFT 会保留 Bluestein 的内部 physical shape（例如 `1000→2048`），输出校验仍针对原始 logical shape。该组使用内部组合路径；直接调用 cuFFT 的 wrapper 不能冒充本方法的性能收益。
`plans` 通过现有公共 API 的 `policy=measure` 比较候选，是有限的多维/组合路径测试，不宣称穷举完整二维设计空间。

小显存卡使用 `16 × input_bytes ≤ 90% global_memory` 的保守包络。超出者记为 `deferred-memory-envelope`，保留原 batch 和合同；这不是硬件不可实现的证明。跨卡图表只比较相同语义的公共子集，同时报告各自覆盖率。确有内存证据后可用新的输出目录和 `--memory-factor` 改变包络，不能在同一实验恢复时偷偷更换范围。

## 4. 恢复、导出与证据边界

运行结果位于 `results/v100-current/<型号>-<显存>-<UUID前缀>/`。重复同一 `--mode run ... --resume` 命令，会复用已完成阶段及相容的 trial；硬件、编译、模板、基线或协议改变会拒绝恢复。

入口发现其他 GPU 客户端就停止，不等待无限窗口，也不终止别人的进程。运行中检测到混跑时，当前阶段目录会改名为 `.excluded-*` 保留原始证据，恢复时重新执行该阶段；此前完整阶段保留。普通失败/手动中断保留相容断点。独占检测为每秒一次，不代替专用测试窗口。

```bash
python scripts/run_research_target.py --mode report --output-dir results/v100-current
```

同步整个目标结果目录，包括 `campaign.json`、`report.json`、`calibration/`、各组 `acceptance.json`/`summary.json`、组合结果和原始日志；stage checkpoint 的 sidecar 也须一起保留。`report.json` 不把缺测、内存筛选或内部 radix2 对照算作外部库胜出。FFT 速度比统一为 `baseline_ms / cuButterfly_ms`。

这里的 `resolved-declared-campaign` 仅表示这份有限实验流程已走完；各组自己的 unavailable、model coverage 和验证状态仍有效，`full_migration_qualified` 保持 false。完整硬件迁移认证仍使用 [统一校准流程](../hardware_profile_install.md) 的更严格覆盖要求。旧 V100/v0.8 数据是历史证据，不会并入本轮同版本结果。

## 本机准备记录（2026-09-21，尚无 v0.9 性能结论）

在 `origin/main` 的 v0.9 源码 `45de6b5` 基础上，本机已在独立工作树
`cuButterfly-v100-v09` 构建 `build-v100-sm70`。设备由驱动信息识别为
Tesla V100-SXM2-16GB，UUID
`GPU-d4ce75f0-dbc9-1934-3142-5342f9b34b09`。该构建使用现有 CUDA
11.8.89、GCC 11.4、Python 3.12 和本机已有的 MathDx 头文件，**并非**上文
CUDA 12.4 的同工具链实验。新框架的 FFT/FWHT/NTT 小型 GPU 校验通过；
research 策略下的 7 项核心 CTest 全部通过。目标机 CPU 预编译 79/79
个 SM70 模块成功，记录在本地生成目录 `results/v100-current/precompile-sm70/`。

尚不能执行本轮硬件校准和正式性能对比：当前 NVIDIA 内核模块为
`580.173.02`，用户态 NVML 为 `580.178.04`，`nvidia-smi -L` 报
`Driver/library version mismatch`。虽然旧/新构建的 CUDA 小型正确性
测试可以运行，实验入口无法可靠地验证目标 UUID 和其他 GPU 客户端，
因此不绕过独占检查，也不导入旧 V100 或 A100 的测量行。

管理员恢复匹配的 NVIDIA 内核模块与用户态驱动后，先确认
`nvidia-smi -L` 和目标 UUID 的进程查询均正常，然后在上述独立工作树
继续运行（同一 CUDA 11.8 构建和输出目录）：

```bash
python3 scripts/run_research_target.py --mode run \
  --gpu GPU-d4ce75f0-dbc9-1934-3142-5342f9b34b09 --cuda-arch 70 \
  --build-dir build-v100-sm70 --nvcc /usr/local/cuda-11.8/bin/nvcc \
  --mathdx-root ../cuNTT-v05/external/mathdx/nvidia/mathdx \
  --output-dir results/v100-current --resume
```

如改用 CUDA 12.4 或更新 MathDx，必须重新构建、重新预编译，并使用新的
校准输出目录；不能混合两套工具链的 checkpoint 或计时。
