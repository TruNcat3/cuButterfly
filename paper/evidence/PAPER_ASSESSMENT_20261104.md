# 论文论述与论证评审（2026-11-04）

本评审只读现稿及已有摘要，不修改正文，不运行 GPU、不访问 /sdb、不新增实验。范围为 sections 全部十个 tex、CLAIMS.md、AGENTS.md、research_principles.md，以及 CURRENT_EVIDENCE_20261102.md、BOUNDARY_MAPPING_CHECK_20261029.md 和当前数字宏。采用 systems-paper-writing 的贡献—设计—证据对应原则；这不是相关工作的新检索，也不是代码审计。

## 总体判断

现稿已形成可辨认的系统方法论文：跨领域蝶形依赖共性 → 同算术、同理想强度仍有执行差异 → 依赖闭合与资源需求 → 分层时空组织 → 子图执行、交接布局和有限缓冲 → 同核心控制与外部、应用结果。它已超过“框架原型加若干优化”的阶段，有具体构造、可复现实证和保留负结果的诚实边界。但中心贡献“性能表征连接组织与硬件、据此选择”尚未获得与构造本身同等强度的闭环论证。成熟度更准确地说是：**方法与 A100 有界有效性已经成形，完整中心主张及跨架构验证仍在收敛的研究稿**。不能据此宣称已完成跨硬件性能迁移，也无需为此无界追加矩阵。

## 最重要的五个问题

### 1. 中心表征的可操作性仍有一跳：从需求清单到实际组织决策

位置：method.tex:85–164，execution.tex 的 Composing physical services，search.tex:32–63；evaluation.tex:376–424。

闭合区域的大小、理想字节数和容量约束很清楚，但表 1 的四类需求主要是分类，live/aux、ready work、core service 到底如何组成一个可执行选择仍偏抽象。16 点例子证明容量与通信权衡，却未展示“两个都合法的组织，为什么在给定服务与并发约束下选 A 而非 B”。已有 profile 说明选择后的资源变化；外部均值证明选中实现有竞争力；二者都不能单独证明完整表征驱动了选择。Search 对 services/readiness 排序的描述比实验已闭合的证据更强。

直接修稿：将现有贯穿例延伸为一张小决策表，列候选、闭合大小、live/aux、交接、ready work、服务来源和选择依据；没有实测的项明确为解析例。明确哪些需求由依赖精确推导、哪些由 lowering/编译细化、哪些需测量。这可复用现有材料，不需要新矩阵。若真实选择链未接通，正文应说表征“约束并评估”候选，而非暗示所有当前性能结果都由该表征预测获得。

仍缺证据：若坚持“同一完整表征有效指导不同硬件优化”的强主张，需要既定闭环与第二平台的匹配实例。选择 regret 竞赛、全空间最优和新的排序算法均非必要贡献，不应变成额外验收。

### 2. Roofline 动机能证明组织重要，尚不能量化真实资源上界与执行落差

位置：introduction.tex 的 “We first used arithmetic intensity…” 段；motivation.tex:10–58；引言 Roofline 图注。

当前图是 symbolic roof，横轴是 value-only ideal intensity。相同理想强度并不意味着相同实际流量或真实 Roofline ceiling；系数、事务、缓存和 spill 都能改变实际强度。因此现有观测支持“理想复用计数不足以解释吞吐，必须考虑组织”，不能支持已排除资源 ceiling 变化或已测定实际距离上界的因果结论。正文多数地方已限定，但引言 “test whether the gap could be attributed to a different resource ceiling” 和 “isolate the missing variable” 仍比证据强。

直接修稿：将这两处改成对“仅以理想强度解释性能”的反例；把 roof 明确为动机性上界而不是硬件实测模型。保留负载变化的实际数据和硬件变化的解析极限，二者不混画成跨卡实测。无需为动机额外开展全量 Roofline profile。

### 3. 从依赖交集到“无冲突布局”的概括过强，物理映射证据范围需与主张一致

位置：method.tex:160–162；execution.tex:35 起银行映射算法和其后的方形 XOR 示例；evaluation.tex:413；BOUNDARY_MAPPING_CHECK_20261029.md。

交集确定交接的值集合、前驱和发布粒度；它本身不唯一确定无冲突物理布局。Method 的 “intersection determines … its conflict-free layout” 跳过了实际访问组、word width、银行端口、线程指令和地址编码约束。Execution 后面已经给出合适的窄条件，CPU 检查也只证明 bank/offset 双射及两类标量访问组。bank-major flattening 更不能直接当作 GPU interleaved shared-memory 地址。当前文字总体谨慎，但中心方法概括仍容易让人读成一般保证。

直接修稿：将该句改为“intersection derives the handoff; actual producer/consumer access groups constrain a compatible layout”。在算法附近明确 bank/offset 的物理编码需由存储 lowering 实现；方形 XOR 是独立可解释的单字例子。把理论无冲突保证与 GPU 实现的性能收益分开。当前 lack of bank counters 并不否定理论构造，却不能支持通用消冲突加速。

## 已有优点与目前可支撑的主张

- 依赖闭合、边界交集、完整发布的前驱要求和正确组合条件有清晰对象与边界；对 zeta 稀疏依赖和 FFT 全局 twiddle 的提醒避免了共享骨架等于共享数值核心的混淆。
- 单段、单位展开和合作 worker 都作为合法端点出现；逻辑区域不等于 CTA，值驻留不等于 worker persistence，阶段内流水不等于跨阶段 overlap，概念区分明显优于只讲融合或持久化。
- 相关工作承认 SPIRAL/FFTX、Timeloop 等先例及专用库的组织优化；新意定位为蝶形依赖到资源需求的连接，而非声称空间/时间映射、搜索或 XOR 首创。
- A100 外部对照可支持声明的匹配请求上有界竞争力；不能外推所有精度、方向、布局或跨架构领先。FP32 对 VkFFT 只有 5/11 点领先，均值不等于普遍优势。
- 固定各 FFT leaf 的约 1.22× 以及三类 scalar 控制支持收益不完全来自换核心；强参考和负交叉结果说明幅度与组织有关。它们不证明所有机制对所有家族有益，也不等于同预算完整优化器归因。
- CKKS 相对更快 native 方案约 1.131×、逐元素一致，支持短链与指定参数下的完整操作收益。Poisson/filter 支持有界 FP32 应用观察；FNO/QuaRot 显示集成条件与负结果。不可推到生产安全 CKKS 或任务质量。
