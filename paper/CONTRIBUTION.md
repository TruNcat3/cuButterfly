# 贡献收敛：由依赖关系构造蝶形处理范式

## 由真实探索收敛的科学问题（2026-10-27）

用户的研究起点是不同领域中相似的蝶形规律与不同的优化方式。Roofline 揭示了
减少数据物化的机会，但单看静态资源上界仍不足以解释实际运行和扩展表现；固定
核心的组织干预进一步提示，可以从执行组织中寻找跨算术复用的性能规律。
完整因果链、逐章改法与证据要求见 [叙事与证据计划](NARRATIVE_EVIDENCE_PLAN.md)。

本文首先回答的不是某种子图如何构造，而是：

> **对于共享阶段依赖、但具有不同算术与资源需求的蝶形计算，能否建立共同的
> 时空组织性能表征，把资源需求与硬件约束连接起来，在保留专用核心的条件下
> 让高效组织的构造与选择随算术、负载和平台变化而复用？**

“已有高性能专用库为什么还需要统一研究”是核心审稿问题。专用库已有强大的算术
和组织优化，本文要检验这些工作背后的组织规律可以怎样被共同构造、选择和复用。
结构相似只是研究起点；同核心收益、跨算术复现和真实共享路径才支撑统一的价值。
减少代码、适配和调优成本属于可度量的附加收益，不能在缺少记录时当成已证结论。

两项主贡献按“依赖驱动的时空组织性能表征”和“硬件约束下的分层混合数据流”展开，
实现与实验负责验证它们。表征首先刻画状态容量、通信、计算和就绪工作需求，
服务模型再结合具体硬件估计时间，不能把数值拟合本身当成全部研究贡献。
组织可以独立干预，但与核心资源、算术服务率和硬件容量
仍存在交互。各计算类型可以选不同机制与参数，方法有效性也不以逐点超过 cuFFT
作为唯一判断条件。

“任意硬件约束”指约束可作为方法的输入；实际优化要求资源、兼容核心与物理
映射已被表达。阶段和数据维度的空间展开、时间复用各有不同代价，反馈状态可
留在片上，不把时间展开一概视作 HBM 传输。推导与表格见
[方法底稿](METHOD_BLUEPRINT.md)，选择质量及跨平台验证见
[四节实验计划](EXPERIMENTS.md)。

下方日期条目保留此前贡献收敛的推导和来源。本轮正文修改应优先遵循上述问题与
新证据计划，不将历史的机制级中心句直接沿用为整篇文章的中心论点。

## 贯穿实例与证据分工（2026-11-08）

正文用同一依赖构造串联两项已测请求：FWHT 的 8+8 阶段对应每段 4096 个
256 点区域，NTT 的 10+10 阶段对应每段 16384 个 1024 点区域。区域交集导出
交接与等待关系，值宽和核心配置导出资源需求，实际执行分组再决定容量与服务
如何使用。依赖区域数不能当作物理计算组数，NTT 跨独立 transform 的遍历分组
也不是数学边界包。详见 [推导、映射与选择证据](evidence/DECISION_WALKTHROUGH_20261108.md)。

两类请求都保留原端点，全部有限候选可执行，因而本例并不证明容量排除的收益。
在固定算术 leaf 下，FWHT 调优线程数与列分组获得约 1.32/1.37×，NTT 选回
原端点。这检验的是共同规则产生不同组织选择的能力，不要求同一机制处处正收益。
独立的 FFT/FWHT 服务组合研究只支持限定范围内的后验时间预测；不能给上述
NTT 实测选择补写预测值。分层是递归构造和表达能力，性能来自选出的具体组织，
不能把所有组织收益改称单独开关“层次”带来的收益。跨架构证据由用户独立推进
PRO 6000 实验后补充，当前 A100 数据不替代它。

## 2026-10-09 的两项主贡献

1. **统一执行范式。** 从带算术标签的蝶形依赖出发，共用子图闭包、边界交集和
   就绪关系的构造，覆盖不同蝶形算术，而不是仅提供一个包含多个算子的 API。
   SPIRAL/FFTX 已研究统一变换表示与生成，本文需要说明执行构造的具体新增内容。
2. **分层混合数据流。** 同时在 stage/data 维度选择空间分配和时间复用，将局部
   驻留与跨子图流式交接组合起来，并明确容量、发布、重用及后继布局规则。
   贡献在可构造的组织方法及适用范围，不能仅凭“混合”名称宣称无人提出类似并行方式。

两者的关系是依赖分析提供统一对象，分层数据流提供组织选择，子图执行负责落地。
跨核心受控实验检验组织是否有独立贡献，跨算术/负载/硬件实验检验其复用边界。
新增 [相关工作对照](generated/related_work_table.tex) 不使用未经核实的功能勾叉。

2026-09-17。本轮按用户提出的中心观点收敛：深入分析蝶形计算的依赖关系，构造
可复用的执行范式，使算子、负载和硬件平台的变化不再需要逐项重写执行组织。

建议中文表述：

> 基于蝶形计算的阶段依赖与子图交互关系，构建统一的分层混合数据流执行范式，
> 分离算子语义、负载域和硬件实现，并通过依赖驱动的子图构造、布局交接及服务组合，
> 联合选择可执行的高性能组织。

建议英文中心句：

> cuButterfly derives a common execution paradigm from butterfly dependencies,
> separating operator semantics, workload domains, and hardware realizations
> while explicitly optimizing their performance interactions.

这里的解耦是描述和构造过程的分离。核心的寄存器需求、负载提供的独立工作量和
硬件容量仍共同决定最优映射；论文不声称三者在性能上互不相关，也不声称任意新
算子都无需算术适配。

## 动机与贡献的层次

- 动机沿用 APPT 的 Roofline 分析：逐阶段物化使 value-only 强度退化为常数；
  保留中间量提升强度，但受到容量、并行供给及各存储边界服务能力的限制。
- 分层混合数据流同时解决组织选择与可扩展表达。逻辑深度和物化段数不固定为二；
  规模超过选定 leaf 的容量时，可继续分段或递归细分，沿用相同依赖规则。
  这不创造物理存储层或保证隐藏全部通信，也不否定支持任意段数的浅层表示。
- 算子语义模板、负载参数和硬件能力是三个输入；映射是联合优化的输出。描述分离
  的结构依据已给出，其准备成本与适配工作收益需由 E7/E9/E10 量化。
- 子图执行是上述组织方法的实现方式。数学子图及依赖构造在方法章说明；GPU
  ownership、地址、核心调用和同步在执行章说明，不把实现再包装为独立理论贡献。
- 校准和搜索使用近似性能模型。自洽、单位一致、无重复计费是基本要求；排序质量
  和选择损失是有效性证据。模型误差与方法正确性、理论最优性是不同问题。

## 依赖关系怎样产生可执行选择

| 推导 | 产生的对象 | 能省去或统一的工作 | 仍需的适配/测量 |
| --- | --- | --- | --- |
| stage bits Q 的闭合集合 | 2^|Q| 点局部子图 | 同一通信包络下复用分段/局部域推导 | 算术标签、数值契约、core 支持 |
| 相邻组件索引集的交集 | producer/consumer 邻接及交接数据 | 从 bit mask 构造依赖，无需先展开所有标量边 | 物理发布粒度可能更粗；单边图可进一步缩减 |
| P∪Q 与 P∩Q | 边界包、fan-in/out、每条交接的数据量 | 将“能否提前运行”转成可检查的关系 | 多边界包成员会变化，需要完整依赖组合 |
| 后继变动位压到地址低位 | 后继连续布局候选 | 统一 writer-to-reader 布局构造原则 | producer 事务、bank/向量宽度、实际 lowering |
| 局部服务与就绪/重用边 | 物理执行时间及候选排序 | 复用同 regime 的局部测量 | 并发干扰、未见 regime 和最终确认 |

这些关系由正文推导并用 CPU 小实例检查。它们是对现有图块/布局/依赖方法的数学
解释与适用范围，不等于本轮新增了任意布局或任意发布粒度的 CUDA 合成器。

## 可以明确说出的区别

不把 tiling、核心替换、XOR layout 或 evolutionary search 单独称为首创。
本文集中说明：蝶形特定的依赖关系如何产生一组共用的构造规则，这些规则如何
连接不同算术与硬件实现，并以生成覆盖、适配工作量、准备成本和性能验证其价值。
通用编译器可以表达相同程序；比较应关注构造与选择的成本和效果，不预设其不支持。

## 当前算法与源码对应

- 有序分段的邻域采用 split/merge/移动一层，core、layout 和调度轴独立变异：
  `scripts/evolutionary_search.py::_stage_neighbors`、`neighbors`。
- 每个 parent 最多 64 个邻居，当前调用每次最多 32 个 proposal；按 family 保留
  多样性：`evolutionary_candidates` 与 `scripts/calibrate_local_hardware.py` 的搜索循环。
- 历史 seed 优先；之后每四次选择的一次用于 stratum 探索，其余使用模型；projected
  top4 先解析真实 lowering/resource 再评分，correctness 先于 timing。
- 最快的不同已测映射进入 finalist，最终使用确认时间选择。数学合法、lowering
  缺失、服务缺口和预算省略分别记录；没有把这些限制写成理论空间的固定分段。
- `results/comprehensive_20260916/a100-80gb/acceptance.json` 的冻结协议为 16 次
  exploration + 最多 4 次 seed，最多 3 个 finalist。总 screen 不是固定 16。
  等预算比较必须把 seed 计入，并单报 calibration/compile/confirmation 成本。
