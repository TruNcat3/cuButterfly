# 三类实验的口径与 batch 执行合同

长期设计与验证约束见 [全蝶形研究原则](../../docs/research_principles.md)。
本文件仅维护当前实验集合及实际实现状态，不能把 FFT 专项结果扩展成
所有蝶形已完成验证的声明。

本文替代把固定机制点、公共库选择和应用时间并列比较的报告方式。
原始实验和负结果保留。可重建的数据表位于
`results/paper_targeted_20261012/unified_report/report.md`，入口为
`paper/tools/summarize_unified_evaluation_20261012.py`。

## 1. 算子横评

一行对应完整语义请求：算子、精度、shape/rank、batch、方向、输入/输出
顺序、归一化、布局和 placement。每个可用高性能库独立一列，列绝对完整
调用延迟。缺少同语义实现的单元格保留原因，不替换算子或精度。
固定 resident8、手工分段等消融设计点不能进入该表。

已有 E1 的 36 点使用公共 `MEASURE`，目录名中的 fixed 表示固定测试集合，
不代表固定 kernel。10月12日 NTT 12 点另列三进程复测，不与 E1 重复点
混算几何均值。后两轮重放首轮选中 mapping，仅检验时间稳定性。
所有适配的顺序/布局变换计入时间；编译、计划生成和搜索时间单列。

## 2. 机制与消融

每行标出算子/语义、组件、变体及完整延迟，连接 kernel 数、DRAM/L2
字节、shared 冲突、寄存器和等待指标。百分比按 kernel 保留，不把不同
kernel 的百分比简单平均。NCU 计数器解释机制，普通运行测量延迟。

固定映射只在隔离某个变量时有意义。关闭组件后重新搜索的受限最优实验
回答另一个问题，两者分别记录。现有 stagewise 对照 CTA 欠填充，其巨大
比值不是优化过的 stagewise 基线，也不作为对外库领先的证据。
当前已测分段驻留与 FFT 核心×overlap；偏移布局、模型排序/搜索、较合理
stagewise 对照及跨算子组件覆盖尚不齐全，缺测不能由已有图推断。

消融二已有可复用的独立历史实验，不能重复描述成从未实现：

| 历史实验 | 两种核心 | 同核心组织对照 | 已有证据与边界 |
| --- | --- | --- | --- |
| [radix16 core×dataflow](../../results/paper_completion_20260917/core_dataflow_ablation/REPORT.md) | 原生 leaf / cuFFTDx Thread leaf | stagewise-HBM / resident-prefix-2 | A100 80GB 六组、24 cells、72 rows；同核心组织收益几何均值 1.217× / 1.221× |

其固定对象是 `Core::run` 算术 leaf，线程组织、shared 使用、launch 数是
处理变量。例如 N256/B1 两种组织分别为 16 与 256 threads，不能声称
launch shape 相同；stage0 unity-twiddle wrapper 源码也有差异，未经反汇编
不能断言 wrapper 指令一致。该历史独立 binary 不等于当前公共库构建，
其结果支持已测 FFT 实例的组织收益，尚不能覆盖其他蝶形的跨核心结论。
配置说明已在 [core_dataflow_ablation.json](core_dataflow_ablation.json) 中纠正，
保留原始历史记录，不改写历史数值或重跑已完成功能。

FWHT、zeta、structured 存在多种等价实现，但现有 shared-iterative 路径
只允许 scalar/radix2，尚缺第二个明确 leaf 核心的完整交叉。NTT 可构造
固定 radix primitive 的组织对照，但须区分 primitive 固定与整个物理
subgraph core 固定。以上是消融二推广的具体工程边界，不能拿 FFT 的
四格或算术名称标签自动填满全部算子。

### 统一方法与可选机制的验证目标

统一的是蝶形依赖表达、分层组织和映射搜索。驻留深度、分段、布局、
计算核心、流水与 overlap 是可按负载选择的机制，不要求每项机制对每个
算子都加速。某项开关的负结果定义其适用边界；公共选择器是否仍选中
劣势变体，需要另外核验，不能把两类问题混为一谈。

| 问题 | 实验 | 当前证据边界 |
| --- | --- | --- |
| 机制改变了什么 | 同一语义和其他映射参数下开关单个组件，比较延迟与硬件统计量 | 已有驻留诊断与 FFT 核心×overlap；跨算子覆盖未齐 |
| 搜索能否组合机制 | 完整搜索空间与删去组件后重新搜索，记录相同预算及实际测量候选 | 缺少统一、成对的重搜结果 |
| 选择器是否避开劣选 | 用独立复测比较最终选择与已测候选最佳值，报告排序、遗漏与 regret | 不能用校准已完成代替此验证 |
| 自动生成方案是否高效 | 公共调用按完整语义与各外部库比绝对延迟、吞吐 | 使用算子横评表，缺外部对照的类型不宣称领先 |
| 收益能否传到应用 | 同 batch、同数据和完整应用边界，计入转换与集成开销 | 单列应用表，不能由算子加速比推算 |

完整候选集包含受限候选集时，已测最佳值不差于子集是集合关系，不能
独立作为性能贡献。有限预算搜索可能漏掉好点，必须报告实际选出的
方案、搜索开销和候选覆盖。论文的跨算子收益按类型、精度和负载区间
分别统计，保留胜率、分布与弱势区域，不把多个对照库或不同算子合并
后的一项均值当作“各类均提升”的证明。

## 3. 端到端应用

端到端结果汇总按 2026-10-13 的报告约定使用「场景｜类型｜对照｜加速比」。
类型为实际使用的 FFT、FWHT、NTT 等蝶形算子；场景包含输入/batch 和执行
模式，每个对照单独一行，配对比较相同模式，加速比为对照延迟除以本库延迟。
以下任务规划表与原始绝对延迟明细保留各自用途。完整应用包括
padding、变换、频域/量化等主体、输出转换，禁止仅计蝶形阶段。
配套明细列整批延迟、每样本摊销时间和吞吐量，B=1 保留用于比较延迟。
吞吐提升不能单独证明整个应用比竞品更快，两边使用相同 batch。

本轮有限集合如下：

| 应用 | 固定输入 | Batch | 对照 | 重复 |
| --- | --- | --- | --- | --- |
| 二维图像线性卷积 | FP32，512/1024/2048 方形图像，31×31 非对称滤波器 | 1/4/16 | CuPy 原生 padding；Torch 同 padding 单列诊断 | 3 独立进程、轮换执行顺序 |
| QuaRot 完整随机权重 7B | prefill512，decode32，相同模型 hash，SDPA prefill | 1/4/8 | 原生 QuaRot + Dao FWHT | 2 独立进程、交换顺序 |
| FNO | 已有 64/128，B4 | 保留旧数据 | PyTorch/cuFFT | 本轮未重跑 |
| HEonGPU/CKKS | 全 GPU RNS 与完整调用 | 待接入 | 原生 HEonGPU | 无完整应用结果 |

FFT batch 含不同图像，使用同一空间滤波器，每次完整调用重新计算一份
滤波器频谱，三个后端一致；不把重复同一张图、重复调用或 filter 缓存
冒充批处理。变换仅沿最后两个轴，batch 不参与卷积。
QuaRot 随机权重只验证实现一致性和执行时间，不证明模型任务质量。
FFT 继续仅报告完整误差分布，未设通过阈值；QuaRot 沿用已通过的逐位
一致性门禁，新增 batch 若不一致则报告失败，不自动放宽。

## 4. 校准、tuning 与应用调用的实际接线

安装后的 rank1 registry 与 xD 完整计划选择器目前是不同路径。
rank1 `DEFAULT` 可以读取兼容 registry；xD 在 cache miss 时执行完整
计划候选测量，没有读取 rank1 校准曲线。将校准 manifest 写入 provenance
并不等于该数据参与 xD 选择。现有 `tune_hardware.py` 也仍以 rank1
workload 为主，不能宣称已提供全 xD 分层代价模型校准。

本轮通过已有 `cubutterflySetCachePath` 接入 Python Plan 和两个应用
adapter。每 GPU 使用独立 `CUBUTTERFLY_PLAN_CACHE`，另将匹配的 rank1
registry 显式传给应用，避免隐式读到其它构建的默认文件。
缓存 key 含完整语义、硬件型号/显存/SM、平台规则及 runtime fingerprint；
每卡单独文件补上 key 未含 UUID 的边界。文件写入使用已有 flock 保护。

执行分两步：先在计时外使用 `MEASURE` 生成实际应用计划并验证完整输出；
随后各独立进程使用 `DEFAULT`。测量入口的 `--require-cache` 强制每个计划
报告 `user_cache`，否则停止，不把重新搜索或静态回退伪装成已调优重放。
每个计划保存完整 mapping、选择来源/原因和 cache 身份。
这补齐了完整计划的跨进程精调重用，不代表扩展了理论设计空间或完成
xD 校准模型的统一。原生路径和 `fp32_composed` 兼容路径仍分别标注。

首次 batch 运行发现另一个明确边界：xD 调优默认分配预算为 512 MiB，
超出预算时不会测量候选。1024/B16、2048/B4 和 B16 的图像计划因而使用
静态选择，未写入已测量缓存，后续 `--require-cache` 正确停止运行。
这些结果保存在原始 `application_batch`，不纳入调优后性能表。
修订实验为这组 A100 80GB 显式设置 8 GiB 的 xD 调优分配预算，记录在
实验配置中；库仍检查实际空闲显存，不修改 batch、精度或图像尺寸。
该实验配置不改变库的默认安装行为，也不等价于安装校准已经覆盖 xD。

修订 `application_batch/v2` 的 9 个图像配置已完成调优和三轮测量，全部
在 `DEFAULT` 下命中缓存，测量前后缓存身份一致。输入、校准、registry、
脚本和显式预算均写入版本清单；失败/冲突 attempt 的缓存不晋升。
结果继续按浮点误差分布口径报告，并不表示已确定准确性通过阈值。

NCU 字节数和冲突计数只覆盖被采集的 kernel。外部 FWHT 对照还包含
一次 2 MiB 的 D2D memcpy，必须单列，不能把其 kernel-only 流量称为
完整调用流量。与外部库的固定映射诊断另列，不能作为组件消融。

执行入口 `paper/tools/run_application_batch_20261012.py` 分两个独占 lane，
GPU2 运行 FFT，GPU1 运行 QuaRot。每步通过已有独占 guard，冲突结果不进入
release；遇数值/执行失败停止对应 lane，保留另一 lane 正常工作。原始数据
写入 `application_batch` 新目录。默认只准备命令，`--run` 执行；必须给带
时区的有限 `--until`，不擅自延长等待窗口。

2026-10-12 13:00 状态：FFT v2 已完成四步（调优及三次独立进程测量）；
QuaRot 的原 v1 队列仍在 GPU1 调优，保留其运行，不重复启动 v2 模型。
两者不能因使用同一天的目录而合并版本。后续重启入口要求显式 `--revision`，
正式新队列使用成功 receipt、每次尝试独立缓存及身份核验，不能仅凭
`release` 目录存在就复用结果。
